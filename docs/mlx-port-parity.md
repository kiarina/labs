# MLX 移植の parity 検証

PyTorch 実装を MLX へ移植し、参照実装との一致を検証するときの手順と落とし穴。
2026-08-25 から 08-26 にかけての Mage-VL 移植
([検証方針](mage-vl-mlx-port.md))で実際に確認した内容をまとめたもので、
他のモデルで同じ結論になるかは未検証。新しい移植で反証が出た場合はこの文書を更新する。

## 一致検証は float32 で行う

**異なる backend の bfloat16 同士を比較しても、一致は判定できない。**

Mage-VL(vision tower 24 層 + decoder 36 層)で観測した値。実装は同一で、
dtype だけが異なる。

| 比較 | vision tower cosine | greedy 64 token |
|---|---:|---:|
| MLX fp32 vs PyTorch fp32 | 1.00000000 | 3 枚とも完全一致 |
| MLX bf16 vs PyTorch-MPS bf16 | 0.9988〜0.9992 | 7〜61 / 64 |
| PyTorch CPU bf16 vs PyTorch MPS bf16(同一実装) | 0.99953 | 完全一致 |

3 行目が重要で、**公式実装自身を 2 つの device で走らせただけでも
cosine 0.9999 には届かない**。したがって「cosine 0.9999 以上」のような gate を
bfloat16 で評価する設計は、最初から到達不能である。

実務上の指針。

- gate の数値評価と greedy 一致は float32 の fixture に対して行う
- bfloat16 は実行時精度として扱い、実測値(速度、memory、出力例)を記録する対象にする
- bfloat16 の不一致を見つけても、まず float32 で比較し直してから
  実装の誤りを疑う

## 実装の誤りと数値精度を切り分ける

bfloat16 で一致しないとき、原因が実装か丸めかは次の順で切り分ける。

1. **float32 同士で比較する。** 一致すればロジックは正しく、原因は丸めである。
   Mage-VL では fp32 で相対誤差 1.07e-05、cosine 1.00000000 だった
2. **層ごとに誤差を追う。** 特定の層で跳ねるなら実装の誤り、
   全層で単調に累積するなら丸めである。Mage-VL の bf16 は後者だった
   (layer0 で 5.4e-3 → layer23 で 9.8e-2)
3. **単一演算を float32 化して効果を見る。** 解消するなら、その演算の精度が原因。
   Mage-VL では LayerNorm の fp32 化で cosine 0.998796 → 0.999123 と
   わずかに改善しただけで、attention の fp32 化はむしろ悪化した。
   単一演算の問題ではないと判断できる

相対誤差は比較する位置で大きく変わる点に注意する。値のノルムが小さい正規化直後は、
同じ絶対誤差でも相対誤差が大きく出る。層をまたいで比較するときは
絶対誤差と相対誤差の両方を見る。

## gate は指定された module に同一入力を与えて測る

「ある module の誤差が X 以下」という条件は、その module に**参照側と同じ入力**を
与えて測る。end-to-end で測ると上流の誤差を含み、条件の意味が変わる。

Mage-VL の SSM ブロックでは、end-to-end の出力誤差が 1.2e-05〜1.4e-05 で
基準の 1.0e-5 を超えたが、切り分けると差は SSM ではなく上流の平均プールと
Linear で生じており、SSM 単体に同一入力を与えると 2.7e-07〜4.4e-07 だった。
条件を満たすか否かの結論が逆になる。

## 閾値のある出力は bfloat16 で反転しうる

確率を閾値と比較して 2 値を出す設計では、bfloat16 の丸めだけで判定が反転する。
Mage-VL の streaming gate では、float32 で `p_speak` 0.5022 の時刻が
bfloat16 では 0.4977 になり、speak が silent に変わった。
閾値から離れた値しか出ない入力では反転しない。

検証時は、**閾値付近の値を含む入力を意図的に用意する**。すべての値が閾値から
遠い入力しか使わないと、実装が壊れていても一致してしまう。
判定の再現性が要る用途では float32 で動かす。

## fixture に何を含めるか

最低限、次を固定入力ごとに保存する。

- processor の出力すべて(`input_ids`、`pixel_values`、位置情報など)。
  前処理の一致を独立に検証できるようにする
- 中間出力。vision tower のように差し替え単位となる module の出力を
  forward hook で取る
- 最終位置の logits
- greedy の token 列

あわせて、checkpoint の revision、参照実装の commit、入力ファイルの hash、
dtype、device、ライブラリのバージョンを記録する。

生成コストは device と dtype で桁違いになる。M4 Max で 4.7B parameter の
モデルを forward + greedy 64 token した実測。

| device / dtype | 所要 |
|---|---:|
| CPU float32 | 約 35 秒 |
| MPS bfloat16 | 約 6 秒 |
| CPU bfloat16 | 約 245 秒 |
| MPS float32 | 完走しない(後述) |

CPU は float32 の方が bfloat16 より 7 倍速い。CPU の bf16 は emulation のため。

## 重み変換の gate

変換直後に、参照の全 key が移植側の parameter と過不足なく対応することを確認する。
Mage-VL では 696 key で missing / unused / shape 不一致がいずれも 0 だった。
これは安く、実装の取り違えを早期に検出できる。

`nn.Conv2d` の kernel size と stride が等しく、入力が 1 patch 単位で与えられる場合、
その畳み込みは行列積と等価なので、変換時に `Linear` の重みへ畳んでよい。

## 前処理を bit 一致させる

前処理は演算順序まで合わせれば bit 一致する。合わないときは順序を疑う。

- **transformers は rescale 係数を mean / std に畳み込む**。
  `x / 255` してから正規化するのではなく、mean と std を 255 倍して
  0..255 の値をそのまま正規化する。素直な実装では float32 の 1 ULP
  (4.77e-07)ずれる
- resize の実装(PIL / torchvision / OpenCV)と補間方法は参照実装の分岐に合わせる。
  参照が「A が使えれば A、なければ B」という構造の場合、
  自分の環境でどちらが選ばれているかを実行時に確認する
- 位置情報の生成規則は仕様を読むだけでなく実物を出力して確認する。
  Mage-VL では動画の位置情報の時間軸が 0..T-1 ではなく実 frame 番号だった

## 数値一致は機能の正しさを保証しない

移植した component が数値的に一致していても、**与えている入力表現が
参照の運用と違えば、機能としては働かない**。

Mage-VL の streaming gate は、参照実装に対して最大絶対誤差 2.7e-07 で一致した。
それでも frame-sampled 入力では実際のイベント(ドアが開く、ゴールが決まる)に
まったく反応せず、確率は 0.001 前後に張り付いた。公式が既定とする
codec 入力に変えると、同じ動画・同じ実装で最大値が 0.0009 → 0.8139 に変わった。

したがって、

- parity が通ったら、その経路の**機能そのもの**も確認する。
  検出器なら検出させ、分類器なら分類させる
- 期待した挙動が出ないとき、実装を疑う前に「参照は本当にこの入力で
  動かしているか」を確認する。公式スクリプトの既定引数を読むのが早い
- component を単体で切り離して動かせるなら、その挙動が入力によって
  どう変わるかを見る。Mage-VL では SSM を迂回しても同じ傾向が出たため、
  低スコアが SSM 実装に起因しないと切り分けられた

## 補助出力より最終出力のほうが判別的なことがある

model が補助的なスコア(gate、分類ヘッド、確信度)を出す場合でも、
**最終的な生成物のほうが目的の判別に使えることがある**。

Mage-VL の streaming gate は、グラスが落下するクリップで
確率が 0.45〜0.52 に団子になり、イベント区間と静止区間を分離しなかった。
一方、同じセグメントの生成文は「remains static, no noticeable changes」系と
「Suddenly, a clear glass container starts to move」系に綺麗に割れ、
イベントの時刻まで正しく述べていた。

補助出力が期待どおり働かないとき、それを閾値調整で救おうとする前に、
**最終出力に同じ情報がより明確な形で出ていないか**を見る。
その場合、補助出力は「安い足切り」として使い、判定は最終出力で行う構成にできる。

## 効率の主張は baseline を明示する

「N% 削減」という主張は、比較対象を変えると符号が変わりうる。

Mage-VL の codec 経路は、均等 frame サンプリングと比べて

- カバレッジを揃える(全 frame を見る)なら **95% 削減**
- 固定 32 frame 予算と比べるなら **71% 削減**
- 短いクリップの既定設定(8 frame)と比べると **codec のほうが多い**

いずれも同じ測定値からの計算である。報告するときは、
「何あたりで正規化したか」(この例では見た source frame 数)を必ず書く。
速度も同様で、prompt 長が変われば素直に変わる。

## 参照が外部バイナリを呼ぶなら container 越しに差し替えられる

参照実装が外部バイナリに依存し、それが移植先の OS で動かない場合でも、
**バイナリのパスを環境変数などで差し替えられるなら、container 内の実体を
呼ぶラッパーに置き換えられる**。

Mage-VL の codec 前処理は Linux 専用の `cv-preinfer` を必要とするが、
`CV_PREINFER_BIN` で差し替えられた。引数の `--video` と `--out_dir` は絶対パスで
渡されるため、その親ディレクトリを container 内の同じパスに bind mount すれば
引数がそのまま通る。結果として、**参照実装を 1 行も変えずに macOS で
Linux 専用経路を実行できた**。

確認する順序としては、

1. 参照が外部バイナリをどう解決しているか読む(`shutil.which`、環境変数、設定)
2. 差し替え可能なら、同じ引数を受けて container で実行するラッパーを書く
3. パスは host と container で同一にする。変換すると引数の書き換えが要る
4. 生成物の所有者に注意する(`--user $(id -u):$(id -g)`)

参照が結果をディスクにキャッシュする設計なら、ラッパーすら不要で、
container で生成した成果物をキャッシュ位置に置くだけで済むこともある。

ただし**そのキャッシュをストリーム処理へ持ち込まない**。参照実装のキャッシュは
同じ入力を繰り返し処理する前提で書かれており、入力パス単位で保持して削除しない
ことが多い。ライブ入力は同じ区間を二度処理しないので、キャッシュは効かずに
ディスクを食うだけになる(Mage-VL の codec 前処理では 1 区間約 574 KB、
1 秒 stride で約 2 GB/時)。呼び出し側でキャッシュ位置を差し替え、使用後に削除できる
経路を用意する。

**参照が受け付ける入力形式を、自前で生成する前に確かめる。** 圧縮ストリームを
解析する参照実装は、コンテナではなくビットストリームの種類を選ぶ。Mage-VL の
`cv-preinfer` は H.264 / HEVC を解析できるが、OpenCV の `VideoWriter` が既定で書く
MPEG-4 Part 2 と、VP9 では `KeyError` で落ちた。自前で動画を書き出して参照へ渡す
経路を作るときは、**参照が実際に読めるコーデックで書く**。

形式だけでなく**下限も確かめる**。同じ参照は 1 グループあたり 8 フレームを要求し、
4 フレームでは別のエラー(`no canvases produced`)になった。UI や API から入力の
長さと fps を自由に選べるようにするなら、参照が成立する組み合わせかどうかを
呼び出し前に検証し、参照の traceback をそのまま利用者へ出さない。

## macOS 固有の落とし穴

- **PyTorch MPS の bf16 → fp32 キャストがハングする。**
  `copy_cast_kernel_mps` 内の Metal shader dispatch で進捗なく滞留する。
  73 分間 swap もメモリ逼迫もない状態を確認しているため、待たずに CPU へ切り替える。
  長時間終わらないときは `sample <pid>` でスタックを見ると早い
- **CUDA 専用パッケージは install 自体ができないことがある。**
  `mamba-ssm` は setup.py が `torch.version.cuda` を parse するため、
  それが None の macOS では `InvalidVersion` で失敗する
  (`MAMBA_SKIP_CUDA_BUILD=TRUE` でも同じ)。
  参照が作れない場合、その module だけを公開されている参照アルゴリズムから
  pure PyTorch で再実装して参照とする方法がある。ただし
  「公開アルゴリズムとの一致」であって「公式が実行する kernel との一致」ではない。
  何を検証し、何を検証していないかを lab に明記する
- **CUDA 前提の依存を持つ checkpoint は、import 検査で止まる。**
  transformers の `check_imports` は remote code の top-level import を静的に見るため、
  実行時に使わない module でも install されていないと失敗する。
  実行時に遅延 import される機能なら、空の stub package を venv に置けば通せる。
  ただし **stub を置いた機能は動かない**ので、その機能を検証する段になったら
  別の手段が要る
- **checkpoint の revision を固定する。** 固定しないと remote code の新版が
  実行中に再ダウンロードされ、再現性が失われる
- remote code は宣言された用途以外の依存を持つことがある。Mage-VL は
  静止画経路でも `cv2` を import した
- **`mx.get_peak_memory()` は必要メモリの見積もりに使えない。** MLX の buffer cache は
  そのプロセスが行った全確保の高水位を保持し、処理を止めても OS へ返さない。
  macOS の `footprint` はこれを含むため peak の 2 倍以上になり、64 GB 機でも
  MLX peak 22 GB の時点で swap が 17 GB まで増えた例がある。`footprint` の
  `IOAccelerator (graphics)` は Metal の予約ではなく MLX の active + cache とほぼ一致する。
  必要量は**実際に使う最大設定の footprint** で見積もり、長時間プロセスでは
  区切りごとに `mx.clear_cache()` を呼ぶ。`RSS` は逆方向に動くことがあり指標にならない
- **cold start はマシンにつき 1 回で、プロセスごとではない。** 大きな重みを持つモデルでは
  最初の 1 回だけ推論が大きく遅くなるが、これは mmap された重みの初回 page-in であり、
  以降は別プロセスでも OS の page cache が効く。プロセス起動ごとの固定費として
  一般化しないこと。cold と warm を分けて集計しないと、この 1 回が中央値を歪める

## 記録

観測した事実と解釈を分け、失敗した試行も残す。上に挙げた落とし穴は、
いずれも最初の実行で踏んで原因を追った結果である。追試する人が同じ時間を
使わずに済むよう、失敗とその原因を lab に書く。
